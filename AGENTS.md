# Agent instructions

## Learning comes first

The user wants to learn. Default to teaching, explaining the reasoning, and using
small examples and explanatory comments unless the user asks otherwise.

- Start with the idea and explain why it works. Define unfamiliar terms and use
  small examples tied to the code being discussed.
- For questions and learning exercises, offer guidance, hints, or a partial
  snippet (for example, a component skeleton with the key part left out) before
  a complete implementation. Leave room for the user to work through the solution.
- When the user explicitly requests an implementation, edit, or fix, carry it
  out and explain the meaningful decisions. Do not require extra confirmation
  merely because teaching is the default.
- In source files, prefer comments that explain intent or why a choice was made
  rather than narrating obvious markup or syntax.
- Match the requested level of detail. Instructions such as "just implement it"
  or "keep it brief" override the teaching default for that task.
- Be clear and patient without being patronizing. Explain tradeoffs and correct
  misconceptions directly; distinguish facts from assumptions.

## Repository context

- This is an Astro 7 presentation template using Tailwind CSS 4, TypeScript
  (`astro/tsconfigs/strict`), and `astro-icon` with the Lucide icon set.
- Routes live in `src/pages/`, the page shell in `src/layouts/`, reusable UI in
  `src/components/` (base building blocks in `src/components/templates/`),
  global CSS in `src/styles/`, and processed images in `src/assets/`.
- Slides are a content collection: Markdown files in `src/content/slides/`,
  with their frontmatter schema defined in `src/content.config.ts`.
- `astro.config.mjs` registers the Tailwind Vite plugin and integrations.
- pnpm is the package manager; `pnpm-lock.yaml` is the lockfile.
- `devenv.nix` configures the development environment (Node.js, pnpm) and Git
  hooks. Enter it with `devenv shell` when needed.
- `.pre-commit-config.yaml` is generated by the Nix configuration. Change its
  source configuration rather than editing the generated file manually.
- `dist/` and `.astro/` are build output; do not edit them by hand.

## Development

When starting the dev server, use background mode:

```
astro dev --background
```

Manage the background server with `astro dev stop`, `astro dev status`, and `astro dev logs`.

## Working approach

- Read the relevant code and any more specific `AGENTS.md` instructions before
  changing files. Follow existing naming, structure, and conventions.
- Keep changes focused on the request. Avoid unrelated refactoring, dependency
  additions, or formatting across the repository.
- Prefer simple, readable solutions and explicit behavior over cleverness or
  speculative abstractions.
- Preserve existing user edits and untracked files. Do not overwrite, revert,
  or delete work you did not create without authorization.
- Make reasonable assumptions for routine choices and state consequential ones.
  Ask when missing information materially affects correctness or scope.
- Do not commit, push, publish, or perform destructive Git operations unless
  requested. Never include credentials or secrets in code, logs, or messages.

## Astro and TypeScript

- Honor the Node.js version in `package.json` `engines` and the versions pinned
  in `devenv.nix`.
- Keep work server-side by default. Add client-side JavaScript (`<script>` or
  `client:*` islands) only when the feature needs interactivity, and pass server
  data to scripts through `data-*` attributes.
- Type component props with an `interface Props` block. Use descriptive names and
  small components; follow the surrounding code's style.
- Prefer Tailwind utility classes; use scoped `<style>` blocks when utilities get
  unwieldy. Avoid `is:global` unless the style is truly global.
- When changing slide frontmatter, update the schema in `src/content.config.ts`
  and every slide that relies on it together.
- Treat `set:html` as unsafe for untrusted input; never use it to render content
  that has not been sanitized.

## Validation and handoff

- The relevant check is `pnpm build` (also validates content collection
  frontmatter). Use `prettier --write` only on files you changed.
- For visual or behavior changes, check the result in the running dev server when
  appropriate, and report what was actually viewed.
- Documentation-only changes generally do not need build or visual checks.
- Respect the user's explicit instructions about running checks or tests.
  Report what was actually run, any failures, and anything left unverified.
- Finish with a concise explanation of what changed, why, and any material
  limitations. Include relevant file references and a short learning takeaway
  when it helps the user understand the work.
